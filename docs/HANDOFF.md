## How the pieces connect
- `backend/app/lab/hub.py` (`Lab`) is the hub: it owns the database, the mode and the job runner. Mixed into it: `lab/testlab.py` (plans, runs, Evidence Lab), `evidence/export.py`, `fixes/changes.py` (where every fix stands, and every action on it), `fixes/views.py` (the Fixes views), `migration/state.py` and `migration/system_changes.py`. The routes are in `backend/app/web/` (one file per step; `main.py` only includes them); every route needs the login. A one-page map of all folders is in `docs/LAYOUT.md`.
- A test is a **locked spec** (`engine/research.py` builds it; `canonical.py` fingerprints it). `run/execute/*` runs it and returns raw outcomes only. `engine/reviewer.py` is the **only** place with pass/fail logic, and since 3a also the only place that decides whether a change is offered (`review_proof`). It imports only `engine/vectors.py`, `engine/pq_vectors.py`, `canonical.py` and `checks/tls_names.py`. `present/results.py` and `present/fixes.py` (and the other `present/` files) turn stored verdicts into plain words and decide nothing.
- **A fix is worked out, never stored.** `Lab.fix_states(plan_id)` reads the append-only records (`code_connections`, `changes`, `proofs`, `proof_reviews`, `pull_requests`, `approvals`, `merges`, `run_code`) and works out the status each time. Every proof verdict passes the read gate: the review is redone from the stored rows, and if it no longer gives the stored answer the proof "can't be trusted".
- **A proof** is one `proofs` row plus ordinary `test_runs` rows with phase `proof` (the proof's id sits in `retest_id`; no column was added, so a phase 2 database still opens). It goes through the same job runner and reviewer as a first run.
- **Only our own components run.** `fixes/changes.registered_version` compares the file a change produces, byte for byte, with the registered demo components; only then does that registered component run, never the changed file.
- `fixes/gitrepo.py` reads and writes git's own format with the standard library (no git program, no dependency). `demo_repo.py` (top of `app/`) makes the bundled repository `demo/repos/acme-sign.git/` from the 1.4.2 file (`python -m app.demo_repo`; a test fails if they drift apart). Each imported file gets its own copy in `data/repos/plan-<id>/`.
- **Targets (3a fixes).** A software test's `target.claim` is the ref of the claim naming its program, so `acme-sign 1.4.2` and `acme-sign 9.9` are two targets. `lab/testlab._program_of` says which program a test runs and whether it is the plan's **own** program (`_own_program`: the first of ours in the file). Only the own program runs on the version a retest or proof names (`_submit`); in a proof the others are `other_program` and judged like server tests (`engine/reviewer.review_proof`). `_groups`, `_not_tested`, `_missing_targets` build the grouping, the box and the catalog. All words for Verify rows are in `present/plain.py`; for results, `present/results.py` sets `w.plain` per kind.
- `engine/research.propose_change` holds the one fix template (the range check). Only it and `present/fixes.TEMPLATE_WORDS` know about that particular fix.
- **Polling:** the Fixes view and the Evidence Lab view each carry `busy`, read first. The screens ask again once a second while it is true.
- Frontend: `App.tsx` (step bar and shell), one screen file per step in `frontend/src/components/`, the Fixes parts in `components/fixes/`, shared pieces in `ui.tsx`. `api.ts` keeps the request functions and re-exports the generated types from `api.gen.ts`. The frontend draws only what it is sent: every word, status and button comes from the backend.
- **Generated screen types (4c+).** The shape of each view is written once, in `backend/app/web/models.py`; each route names it with `responses=shows(models.X)` (documentation only). `backend/tools/api_schema.py` writes `frontend/src/api-schema.json`; `cd frontend && npm run gen:api` writes `frontend/src/api.gen.ts`. Backend tests check every JSON answer against its route's shape (`backend/tests/api_shapes.py`). To change a view: backend, then model, then the two generators, then the frontend.
- More detail: `docs/ENGINE.md` (records, the offer rule, the views and routes) and `docs/ADAPTER.md`.

## Server TLS suggestion: what was checked (in 3a it was text only; since 4b it is also a change box on the Acme Pay demo server)
The lines below are still the suggestion's text. Tested on real nginx 1.24.0 and Apache 2.4.58 (OpenSSL 3.0.13) on the build machine, probed with the app's own `tlsprobe`. The app counts a version as refused only on the protocol_version alert, and these settings give exactly that.
- **TLS 1.3 only:** nginx `ssl_protocols TLSv1.3;` · Apache `SSLProtocol -all +TLSv1.3` · Python `context.minimum_version = ssl.TLSVersion.TLSv1_3`.
- **Keep TLS 1.2 with strong suites only:** nginx `ssl_protocols TLSv1.2 TLSv1.3;` plus `ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;`; Apache `SSLProtocol -all +TLSv1.2 +TLSv1.3` plus `SSLCipherSuite` with the same list. The old suite (ECDHE-ECDSA-AES128-SHA) is then refused. These lines don't touch the TLS 1.3 suites. Both lines are needed.
- **Pitfalls seen:**
  - Adding a second line beside the old one doesn't work. nginx adds the lines together, and in Apache the last line read wins without a warning. Change every existing line instead, including any in a site's own block.
  - nginx takes `ssl_protocols` from the default server of an address and port, for every site on it. Put the line in the http block with no per-server lines, or in every server block on that address.
  - In Apache a line inside a VirtualHost beats the main config. Connections that name no site land on the first VirtualHost, and the app sends no site name for IP addresses.
  - Apache needs the plus signs: `SSLProtocol TLSv1.2 TLSv1.3` means TLS 1.3 only.
  - Nothing changes until the server reloads. A failed nginx reload keeps the old settings.
  - Neither server logs the TLS version unless you add it (`$ssl_protocol` in an nginx `log_format`, `%{SSL_PROTOCOL}x` in Apache). Only requests are logged.
- **The AWS names are from memory** (three independent recalls agreed; the AWS docs site is blocked here): `ELBSecurityPolicy-TLS13-1-3-2021-06` for TLS 1.3 only, and `ELBSecurityPolicy-TLS13-1-2-Res-2021-06` for TLS 1.2 and 1.3 with only ECDHE AES-GCM on 1.2. Both are for Application and Network Load Balancers. Do not use `ELBSecurityPolicy-TLS13-1-2-2021-06`: it adds CBC suites.
- **The app's test checks TLS versions only.** After option 2 and a corrected file it passes even if the old suite were still on, so the suggestion says so. After option 1 the file needs no change.
- **Build rule for the words:** the test records only the cipher suite each handshake used; it does not scan for others. The suggestion names a suite, and calls it "older", only when the recorded TLS 1.2 handshake used an old CBC/SHA-1 suite such as ECDHE-ECDSA-AES128-SHA.
- **The warning comes first,** above the exact settings, so nobody copies a TLS 1.3-only line before reading it.
