# Isogeny Evidence Lab: crypto MVP spec

This is the full spec for the MVP, built from scratch in the `prototype` repository on branch `mvp/crypto-simple`. `CLAUDE.md` holds the standing rules; this file holds what to build. Build one phase at a time (section 9).

**The goal:** a simple, working demo that shows investors one thing: **you bring in a file that claims how a system's encryption is set up, and the product tells you, with evidence, whether each claim is true, then suggests the fix.** It must be accurate, and it must be simple: few screens, few buttons.

**Out of scope:** accounts beyond one local login, teams, approval workflows (other than the pull request approvals in section 7b), compliance reports, scheduling, other industries, any AI model (until phase 5c: since then Otto uses Claude for four named jobs under the rules of section 3, and the co-pilot stays rule-based), any outside orchestration service, Cairn, and any code from the old prototype.

## Why this exists (context for your decisions; don't put this text in the app)

- **Who uses it:** usually one security engineer at a company that handles sensitive data or payments. They are busy and not a cryptographer. Design for them.
- **The pain:** scanning tools produce lists of where encryption is used, but nobody checks whether the list is true. Encryption is tested once and rarely rechecked. Auditors want proof, not a list. The move to post-quantum encryption makes all of this urgent.
- **What we do differently:** we don't replace the scanner. We take its list, prove each claim with real tests, suggest the fix, and retest after the change, with evidence anyone can check.
- **What this MVP must show investors:** it works on a real flow, it's accurate (it catches the planted problems and doesn't flag the true claim), and it's simple enough to understand in five minutes.
- **How to use this:** when a choice isn't covered here, pick whatever makes the demo simpler, clearer or more accurate. If a feature doesn't help one of those three, leave it out and list it in `docs/LIMITS.md`.

**Why crypto-agility needs proof (added in phase 4a).** Crypto has to keep changing: post-quantum migration, newly published bugs, new standards and deadlines. That's crypto-agility, and other products sell the ability to switch: wrappers, policy engines, certificate rotation. They don't check that the crypto underneath, or its replacement, actually works. Evidence Lab's job is proof: test the crypto itself, recommend changes, offer fixes only with proof, and keep evidence after every change. Phase 4a applies that to the post-quantum migration (section 7d).

## 1. The flow (six steps, with the co-pilot beside them)

1. **Import.** The user uploads a file from a scanning tool that lists where encryption is used and how (for example "this server only allows TLS 1.3", "this service signs with ECDSA P-256").
2. **Verify.** The product checks each claim against the real system and marks it **True**, **False** or **Couldn't check**, with the evidence behind it.
3. **Test plan.** The product suggests five tests. The user can reorder them, remove them, add new ones from a short catalog, and run them one at a time or all at once. Since phase 5b the test plan sits on the **Checks** page, and every check the app runs, wherever it is started (Verify, the test plan, a retest, a fix proof, a try on a test copy, the measurement after Apply or Roll back, Migration's Measure status, Dependencies' measurements), shows on Checks and in Evidence.
4. **Evidence Lab.** Shows each test's result, what it proves and what it doesn't, and for each failure one line that points to its fix in the Fixes step. After the fix (in the demo, a corrected version), the user reruns the same tests and sees before and after here.
5. **Fixes.** Holds the suggested fix for each failure. For a code fix: the exact change, the proof that it works (every test rerun on the changed code), and a pull request that people approve and merge (section 7b). The app never merges or deploys by itself.
6. **Migration (phase 4a).** For every system in the file: its measured post-quantum status, the measured cost of moving, four options with honest trade-offs, a recommendation from fixed rules, the user's own choice, and a phased roadmap (section 7d).
7. **The Otto assistant** (phase 6; until then "the co-pilot"). An assistant in the right-hand panel beside every page of an assessment. It suggests what fits the page (phase 6a, built on 19 November 2026); it takes commands (phase 6b, first half) and answers six fixed questions (phase 6c, first half), both by fixed rules, built the same day. It's an aid, not the decision-maker. The three rules below call it the co-pilot, as before, and stay as they are:
   - **Results never come from the co-pilot.** True/False and Passed/Failed come only from the checks and tests.
   - **Everything is doable without it.** Every action (add a test, reorder, run, retest, mark a finding as reviewed, download) has its own button in the main screens. The co-pilot is never the only way to do anything.
   - **It can offer a shortcut, never act alone.** When it suggests an action, it shows a card with a Confirm button that does exactly what the matching main-screen button does. Nothing happens until the user clicks.

That's the whole product. No accounts beyond a single local login, no teams, no approvals workflow beyond the pull request approvals in section 7b, no compliance reports, no scheduling, no other industries.

The byte-for-byte check comes first: the changed code must be one of our registered demo programs, and so must the code it starts from; the registered program is what runs, never a file from the repository. "Before" is each test's newest reviewed result on exactly the code the change starts from; where there is none, that test also runs on that code in the same run. The separate reviewer reviews every run, and a rule of its own then says what differs from before: that sets the change's status and nothing else. The speed test is timed side by side with the code the change starts from, so that one run is its comparison: "Slowdown found" counts with the tests that fail now, and anything else reads "No slowdown against the code before". These runs are kept apart. They never replace the result of the assessment's own tests, and no proposal of Otto's is made or moved by them.

On Evidence, under Crypto tests, with "Came from: Change watch". While anything runs for the assessment the page asks again every second; a read that fails is said on the page.

It is **Text only**: it has no button, no proof and no pull request. The app writes no change for a developer's branch and never merges one. The change's own panel says so in one line, with **View in Fixes**. The entry goes when the change no longer reads so (it was run again and passes, the branch moved, or the test plan changed and it has not been run since).

"Run the picked tests" can be typed, with "for *the change*" where several can run. The report has part 9, "Change watch". The verify command checks that part against the runs in the file: each run record against its fingerprint and its review, the code and the kind of run each run record names against its place (on the change, or on the code before), the record against the runs, the reviewer's word and its count against the record (by the rule, written out a second time in the verify command), that each change names the newest run of exactly its code and that this run's files and versions are the change's, whether that run is of the tests picked now, that Fixes has an entry for exactly the changes that read "Passed before, fails now", and every Change watch row of the file's list of checks against the part. A file that lists such a run without the part fails. In the report a change that leaves the program alone is said as that, never as code that is not ours; the report lists a change's entry in Fixes under the same heading as the page.
  - **Not built yet (the rest of phase 6d):** the Watch list and its proposals (what is watched, why, what rechecks it), with the pinned checker the plan gives watch runs and watch-list decisions; a watch run's results and flags as entries of the panel's Testing thread; the Related block of a change.

Where it cannot be offered the part says why and has no button: the scanner file does not name the library, the app holds no public copy of that version, the version could not be read, or Retest new version cannot start now (in demo mode, with its own reason).

  - **Part 4, Hypothesis:** what the facts do not show, in the app's own sentences where they apply: "Whether your system really loads this library needs your environment."; "The app has tested the library's public copy, not the programs of yours that use it."; "The app has no dependency data for this version." For a library the app holds nothing about, one sentence says that everything about the update is open. A hypothesis words no result.
  - **The knowledge base** gains one kind of entry: what a version of a library declares it needs, read from the publisher's own package file, quoted, with its link, the date it was read and the fingerprint of the file. Filled for the pinned versions of elliptic and python-ecdsa; Java and OpenSSL have no such file and read "Doesn't apply".

It runs read-only, as an unprivileged user, with no Linux capabilities and small limits, on 127.0.0.1 only; its settings and test certificate reach it through its input, never through a file on this computer. **What runs:** our own demo components, the pinned lab images and (phase 4c) the real libraries below, nothing else.

- **Research engine socket (the autoresearcher plugs in here later).** Everything that thinks about tests goes through one `ResearchEngine` interface: `propose_tests(claims) -> plan`, `design_test(request) -> test` (used by **+ Add test** and the co-pilot), `review(result) -> review`, and `dig_deeper(finding) -> research request`. Phase 2 ships a rule-based engine that returns the five tests in section 7. Our real autoresearcher replaces it later without changing any screen. Build the records to match how the autoresearcher works:
  - **Test before run:** each test is written down before it runs (question, method, inputs, controls, the pass/fail rule) and locked with a SHA-256 hash. A locked test can't change; editing it makes a new version.
  - **Run record:** every run keeps the locked test's hash, the component version, raw outputs, logs and timing. Runs are never edited or deleted, including failed ones.
  - **Separate review:** the result is checked by a separate review step (control behaved as expected, pass/fail rule applied correctly) before it shows as Passed or Failed. The engine that proposed a test never reviews its own result.
  - **Dig deeper:** in phase 2 this saves a "research request" (the finding, the question, the evidence) with status "waiting for research engine". Show it in Evidence Lab as queued; don't fake an answer.
  - Document the interface and these record shapes in `docs/ENGINE.md`.
  - **Since phase 5c, Otto's pack engine sits in the socket** (`OttoEngine`, around the rule-based engine). Everything the rule-based engine did it still does, under its own id, so nothing that was graded before moves: the suggested tests, the catalog, the migration and capability measurements, and the fix template. Two things are new. A test can come from a signed test pack (section 7f): an advisory check is locked like every test and is stamped as proposed by the pack (`isogeny.otto-pack/1`), never by the rule-based engine or the reviewer. And when an advisory check has failed on the assessment's own program, Otto is asked first for the code change (sections 7b and 7f). The reviewer stays what it was: the only place that decides a result, separate from every proposer.
- **The Otto harness (phase 5c).** Otto is Adam's research harness, in the private repository `isogeny-labs/otto`. The app uses it as it is, at **one pinned commit**: `backend/otto.lock.json` names the repository, the commit, the version (0.1.0) and one SHA-256 over the files of that commit. Only the prepare step fetches it (`python -m app.prepare --otto`, which `./run-demo.sh` runs at every start; it needs read access to that repository once, and no Docker), into `backend/.otto/<commit>/`, a folder git ignores (the environment variable `EVIDENCE_LAB_OTTO_HOME` names another folder; the end-to-end walk points it at an empty one to show the app without Otto). Wherever it is kept, the copy is checked against the pinned fingerprint before it is used and is loaded from that folder only. Nothing of it is ever copied into this repository (ours is public, his is private), and the app itself never downloads it. It is standard-library Python, so no PyPI or npm package comes with it; its Rust tool, its Lean prover and its model judge are not used, built or called. The harness is not software under test. It keeps the two ledgers of section 7f and starts only five small scripts of ours: the research agent command, the trial script and the three record checkers (one on the research side; in an assessment's folder one for run and step entries and, since 18 November 2026, one for decision entries). Before the harness may start a record checker in an assessment's folder, the app makes sure that file is a regular file with exactly the bytes of the checker that ships with the app (a link or another program in its place is replaced, never run). A research lab folder is used only when it holds nothing but folders and regular files. A trial goes through Evidence Lab's own lock, run and review path, so a real library still runs only in its container. **Without the harness** the app works as before and says "Otto is not installed on this computer" with the reason (it was not fetched, the copy is not the pinned one, the pin file can't be read, or the computer runs Windows, where its ledger can't lock files); advisory checks then can't be added or run. Moving the pin is a dependency change and needs Kevin's OK (`backend/tools/otto_pin.py`). Approved by Kevin on 17 November 2026 with the phase 5c plan.
- **Otto's use of Claude (phase 5c), recorded and live.** Otto uses Claude for four jobs and no others: on the research side to **read an advisory**, **design a test** for it and **propose a fix** for the library it names; in the app to **write a change for your own program** when an advisory check has failed on it. Nothing Claude writes is trusted by itself (section 7f): it is data, it is checked before anything uses it, it never sets a result, it never acts without a person's click in the app, and it never touches a live system. Every Claude step is kept in a ledger with the full prompt, the full answer, where the answer came from, the model (none for a recorded answer), both SHA-256 fingerprints, the tokens and the cost.
  - **Recorded answers.** `research/recorded/` holds one answer for each exact prompt, found by the prompt's SHA-256. Tests, screenshots and the accuracy check use only these, so they repeat exactly and need no key. The shipped ones were made during the build with no API call, and say so: each is labelled "Recorded during the build, not through the API" and names no model. A prompt with no recorded answer gets "No recorded answer: this needs Live Otto."; nothing is made up in its place.
  - **Live Otto** (Settings, section 2) is off by default and can be turned on only when an API key is set in the `ANTHROPIC_API_KEY` environment variable. The key is read from the environment at the moment of a call and sent only with that request. It is never stored, shown, logged or put in evidence, and its value is removed from every message before the message leaves Otto's client. A value that is not in the form of a key (it holds a space or a line break, say) is never sent, and a request that can't be made is reported by the kind of error only, never in the error's own words, because an HTTP library can name a header's value there. Looking at a page never asks Claude: a live call is made only by a person's click (**Connect demo code**) or by the research command run with `--live`. With Live Otto on and a key present, an answer comes from Claude and never from the recorded answers. What is sent: the advisory text and, for a fix to your own code, the source file of the failing program and the cases it got wrong.
  - **A spending limit per run** (2 US dollars until it is changed in Settings; a run is one fix request in the app or one research command). Otto adds up each call's cost from the tokens the API reports and a price list kept as a config value with its source and date, and does not send a request that could pass the limit. The check is made before every request, the first and each one sent again. It counts the worst case: every byte of the prompt as a token, a full-length answer, the dearest price among the model asked and the models a declined request may be passed to, and both attempts where a declined request can be answered by another model. A request that got no answer that can be read (a time-out, a broken connection, an answer cut off part-way, an answer that is not what the API sends) may still have been billed, so the most it could have cost counts against the limit from then on. In the research command, where each step is its own process, all of this is carried from step to step.
  - **Configuration.** One model answers every step: `claude-opus-5-5`, named in one place (`backend/app/otto/model.py`; the environment variable `EVIDENCE_LAB_OTTO_MODEL` names another). A model that has no price in the list is never called. Where Claude declines a request, Anthropic's API may pass it to another model (its fallback option); the step then records the model that answered and says so, and only the text written after the switch is the answer. The call is made with Python's standard library; no package was added for it.

What an add-on downloads when a Codespace is built is not pinned (`docs/LIMITS.md`).

- Evidence fingerprint: SHA-256 over the evidence file, signed with an Ed25519 key that the app generates on first start and stores outside the sandbox's reach.
- **The Otto assistant (phase 6a; before it: the co-pilot).** Rule-based behind one `CopilotEngine` interface (`read(lab, assessment, page, open item) -> view`, in `backend/app/assistant/`): its suggestions and next steps work with no key, and no AI model is in it. The panel is titled "Otto". Its own code decides, runs and changes nothing: it reads the views the pages draw from, and a decision or a start is sent by the browser to the page button's own route. One read, `GET /api/assessments/{id}/assistant`; that read stores nothing (closed tabs are remembered in the browser; since phase 6b what was said is kept, as below). Since phase 6b (first half) the fixed list of commands is built: `backend/app/assistant/commands.py` holds the list and the rules that read a sentence, `answers.py` finds what the words name and answers with where to go or with a card of phase 6a; two more routes, `GET /api/assessments/{id}/assistant/answer` (a read, nothing kept) and `POST /api/plans/{plan_id}/assistant/messages` (the same answer, and the exchange kept in `assistant_messages`, add-only, written by `backend/app/lab/said.py` outside the read-only package). No model is asked for a command in this version. Since phase 6c (first half) the six fixed questions are answered there too: `backend/app/assistant/questions.py` holds the questions, the rules that read one, and the rules that pick the facts of an answer from the views the pages draw from, each fact with its link; an answer is kept like any exchange, with its facts. No model is asked for a question in this version. The three jobs for Claude with Live Otto on (to map free wording onto the fixed commands, to explain facts the app worked out, and to design a test for a hypothesis), belong to the rest of phase 6 and are described here when each is built.
- **The advisory source (phase 6, Otto's research loop).** One public source, OSV, read with Python's standard library (`urllib.request`; no new package): one POST to `https://api.osv.dev/v1/query` for each package, holding its name and ecosystem and nothing else, by a person's click (`backend/app/otto/lookup.py`). The answer is read as data against the shape OSV documents. `EVIDENCE_LAB_ADVISORY_SOURCE` names a folder of recorded answers that is read instead; the backend tests block the network read (`tests/conftest.py`), as they block Claude's API. ## 4. What the import file looks like

Support two formats:
- **CycloneDX 1.6 CBOM JSON** (the format IBM's CBOMkit produces). Read only the crypto parts: algorithms, protocols, certificates, and where each is used.
- **A simple CSV template** we ship (`location, type, claim, value`, for example `localhost:8443, tls, protocol_versions, TLS1.3`). Since phase 4a it also takes a post-quantum claim (`localhost:8451, tls, post_quantum, hybrid`; the value is `classical`, `hybrid` or `post-quantum only`), which Verify checks with the migration measurement, and optional settings rows for a system (`localhost:8451, system, exposure, internet-facing`; `data_lifespan` is `short` or `long-lived`, `exposure` is `internet-facing` or `internal`, `can_change` is `yes` or `no`). Settings are not claims: nothing checks them, and the user can change them in the Migration step. Since phase 4c a software row can also carry a `key_exchange` claim (`openssl 3.5.9, software, key_exchange, ML-KEM-768`), beside `signature_algorithm`; Verify checks it with one key exchange round trip that an independent library confirms.

**A dependency list (phase 4d)** can be added to an imported file, in the Dependencies view: **CycloneDX JSON 1.5 or 1.6**, or **SPDX JSON 2.3**, with dependencies of dependencies (CycloneDX `dependencies` and nested `components`; SPDX `DEPENDS_ON`, `CONTAINS`, `DEPENDENCY_OF`, `CONTAINED_BY` and `DESCRIBES`). Limits: 16 MB and 10,000 components. Anything else is refused with one plain sentence that ends "Evidence Lab reads dependency lists in CycloneDX JSON (1.5 or 1.6) or SPDX JSON (2.3).", and an earlier list stays in place. The newest list is the one in force. It is data: names, versions and package addresses are kept as text and never reach a command line. The CSV and CBOM imports are unchanged.

Turn each into a list of **claims**. Each claim says where (a host:port or a software component), what (TLS versions, cipher suites, key exchange, certificate algorithm and key size, signature algorithm), and the claimed value. Invalid files get a clear error naming the line or field. Nothing in an uploaded file is ever executed.

## 5. Verify: how claims are checked

- **Server claims** (host:port): connect with handshakes only. Find which TLS versions are actually accepted (including older ones), cipher suites, key-exchange groups, and the certificate's algorithm and key size. Compare with the claim. Before checking any address, the user ticks "I own this system or am allowed to test it" once per address. Only allow localhost and addresses the user confirmed. No attacks, no load.
- **Software claims** (a signing component): run the component's `info` command (section 6) and compare the algorithm and version it reports with the claim, then do one normal sign-and-verify round trip to confirm it really uses that algorithm. Whether it's built correctly is not a Verify question; that's what the tests in section 7 are for.
- Every result stores the raw evidence (command, output, time, tool version).

## 6. Software under test: the adapter

Software is tested through a tiny command-line contract. It reads JSON on stdin and writes JSON on stdout, with five commands: `keygen`, `sign`, `verify`, `info`, and `bench` (the program signs and verifies many times itself and reports its own timings, so program start-up isn't counted). Document it in `docs/ADAPTER.md` with a complete example. Components come from the demo and, since phase 4c, from the real libraries of section 3.

**Since phase 4c:** two more commands for key exchange, `encaps` and `decaps` (`keygen` is shared); an optional `algorithm` on every call for a library that offers several; optional inputs that replay an official test case exactly (a published test seed, published randomness, a context); and a wrapper for each real library, which only translates and holds no crypto. **What counts as "no" (Kevin's decision, 15 November 2026):** an error raised by the library while checking a signature means the signature was not accepted. When that error is a general program crash and not the library's own "bad signature" answer, the result notes it under **Also noticed**; it is never a result.

## 7. The five suggested tests (and the catalog)

Suggest these five, ordered by what the claims cover:

1. **Server protocol check:** does the server accept anything older or weaker than claimed?
2. **Certificate check:** do the certificate's algorithm and key size match the claim and current NIST guidance? Store that guidance as a config value with its source link, not a hard-coded claim.
3. **Official test vectors:** does the signing component give the right answer on Project Wycheproof vectors for ECDSA P-256 and Ed25519? Vendored (approved): the Wycheproof files pinned to C2SP/wycheproof commit `dab4ea2`, with source URL and Apache-2.0 licence.
4. **Bad-signature check:** does it reject signatures it must reject: changed message, changed signature, wrong length, r = 0, s = 0, values at or above the curve order, broken encodings?
5. **Speed and size:** signing and verification time (median and slowest 1 in 100, with the repeat count shown) and key and signature sizes, compared with a reference library. Timings come from the adapter's `bench` command. This test reports numbers (**Measured**); it has no pass/fail on the first run. On a retest it re-measures the old and new versions side by side and flags a slowdown larger than the measured run-to-run noise (**No slowdown beyond measured noise** or the slowdown found).

Catalog for **+ Add test** (small, at most five extra): post-quantum readiness (does the server offer X25519MLKEM768?), compare with a post-quantum signature (ML-DSA-65 speed and size from a reference implementation, labeled "reference, not production"), plus any you think are essential. Ask me before adding more.

Since phase 4a the post-quantum readiness test uses the same measurement as the Migration step (the probe, its control servers and, where available, full handshakes), so the Tests step and the Migration step never disagree, and it runs in demo mode with no Docker. Its answers are still **Offered** and **Not offered**.

On screen (phase 3a-fixes) test 3 is titled **Independent exam (Wycheproof)** and test 4 **Attacker tricks (our short list)**, so the difference is plain: one is an outside exam of 484 cases, the other our own short list of forgeries. Their ids (`official_vectors`, `bad_signatures`) and the answer key are unchanged.

**The two post-quantum exams (phase 4c).** A program that claims ML-KEM-768 gets the **Key exchange exam (ML-KEM-768)** (`mlkem_vectors`: key generation, encapsulate, decapsulate; 655 cases), and one that claims ML-DSA-65 gets the **Signature exam (ML-DSA-65)** (`mldsa_vectors`: key generation, sign, verify; 475 cases) and Speed and size. They are suggested by themselves, not from the catalog, and take the place of the two ECDSA tests for that program. The cases and their right answers are NIST's ACVP files (usnistgov/ACVP-Server, commit `975de31`) and Project Wycheproof's ML-KEM-768 and ML-DSA-65 files (C2SP/wycheproof, commit `65ca494`), stored whole and pinned by SHA-256 (approved). Answers are compared by fingerprint. Each part has its own control that must fail: a copy that changes one byte of every answer, a copy that skips the two key checks the standard requires, and for verification the accept-everything signer. The 45 NIST cases for the pre-hash variant (HashML-DSA) are left out for every library, and the test says so. Timing attacks (such as KyberSlash) are out of scope; `docs/LIMITS.md` and each result say so.

**Advisory checks (phase 5c).** One more kind of test, for signing programs and libraries, titled "Advisory check: *plain name* (*id*)" (`advisory_cases`). It comes from a signed test pack (section 7f), never from the five suggestions or the catalog: Otto proposes it on Advisories, and it joins the test plan only when a person accepts that proposal. It reruns the published test cases that match one advisory: cases of the same pinned Wycheproof ECDSA P-256 file as the Independent exam, with their ids written into the locked test. **Its control is the accept-everything signer, which must get every must-reject case wrong;** a selection with no must-reject case has no working control and is refused when the test is designed. The reference library must get every selected case right. The rule is the Independent exam's: **Passed** only if every answer is right, and any wrong answer means **Failed**. A failed result says the program gives the wrong answer on published cases of the kind the advisory describes, and lists them; it says nothing about how serious that is. It runs where every signing test runs: our own demo programs in either mode, a real library in isolated mode only (in demo mode it reads **Couldn't run (needs isolated mode)**). It is part of the locked plan, so every retest and every fix proof reruns it, and a change is offered only if it passes on the changed code. Without the Otto harness it does not run and reads **Couldn't run (Otto is not installed on this computer)**, because its run could not be recorded.

Every test has a **built-in control**: alongside the customer's component it also runs a deliberately broken reference component that must fail, so "passed" means something. If the control doesn't fail, the test result is marked **Couldn't trust this run**.

Each result is one of: **Passed**, **Failed**, **Couldn't run** (with why), **Couldn't trust this run**; plus, where the answer key uses them, **Measured**, **No slowdown beyond measured noise**, and **Offered / Not offered** (post-quantum check).

## 7b. Suggested change with proof (built in phase 3a)

Between finding a bug and retesting, the product proposes the exact code change and proves it works before offering it. All of it happens in the Fixes step (section 2); Evidence Lab only links to it.

1. **Connect the code.** The user connects the component's source code with **Connect demo code** in Fixes. In the demo this is a bundled local git repository of `acme-sign` (version 1.4.2), labeled **Demo data**; connecting makes the app's own working copy of it. Each imported file gets its own fresh copy, connected once for that file rather than once for each fix, so the demo can be run again on the same machine, even after a merge, with the same results. Phase 3c reuses the same repository, branch and proof code. Connecting real GitHub or other hosts is out of scope for now; list it in `docs/LIMITS.md`.
2. **Suggested change.** For a failure with a known fix, the research engine proposes a code change, shown as a before/after diff of the exact lines, with a plain-language explanation. The change holds only what the fix needs: in the demo, the range check and the version line. With no AI model connected, changes come from fix templates for known bug types and are labeled **"From a fix template"**. Never present a template change as AI-written. Since phase 5c, when an advisory check has failed on the assessment's own program, Otto writes the change; it is offered, labeled **"Written by Otto"**, only when the rule of section 7f (point 7) holds, and as a proposal that a person accepts before the code is connected (section 7f, point 9). Otherwise the fix template, where it answers the failure, is offered in its place with its own label.
3. **Proof before offering.** The app applies the change to a copy of the code on a new branch, rebuilds the component, and reruns **every** test in the locked plan (not only the failing one), plus the speed comparison. The proof starts by itself as soon as the code is connected; it has no button of its own. It needs a result for every test in the plan to compare with, so **Connect demo code** is switched off until every test has been run (the same rule as Retest). The change is offered only if all three of these hold:
   - every test that runs the changed code passes (official test vectors, bad signatures, and no slowdown beyond the measured noise; a report-only test in the plan, such as the ML-DSA-65 comparison, has no pass or fail and only has to run);
   - every control behaves;
   - the tests that don't run this code (the server tests) are rerun and come out the same as before.

   While the proof runs, the fix's status is **Proving**. If anything fails, show the failed proof and don't offer the change: the status is **Proof failed**, the fix is never called ready, and **Run proof again** is then available. Once the proof has passed, the status is **Ready for review** and, while a server finding is still open, the fix's summary carries this plain line: "This fixes the signing program. The server finding is separate and still open." While the proof is running, or after it did not pass, Fixes must not say the change fixes anything (results come only from tests); it then says: "This change is for the signing program only. The server finding is separate and still open."

   (Decided in phase 3a. Read literally, "every test passes" could never hold in the demo: the server test fails before and after, because a code fix doesn't change the server, and the answer key expects that.)
4. **Pull request.** **Open pull request** creates a pull request inside the app against the connected repository: the branch, the diff, the proof results and the evidence fingerprint. The user picks one or more reviewers who must approve it. Reviewers come from a fixed tick list: "You" (ticked by default), plus "Demo reviewer A" and "Demo reviewer B", labeled **Demo data**. The app has one login, so whoever is at the keyboard records each approval; the screen and `docs/LIMITS.md` say so. Each approval is recorded with name and time. The status reads **Waiting for approval** until every picked reviewer has approved, then **Ready to merge**. The app never merges or deploys by itself; merging is a separate, confirmed user action (**Merge pull request**, then **Confirm merge**), possible only when every picked reviewer has approved. The status then reads **Merged**. The pull request can be downloaded as a patch file (**Download patch**).
5. **Retest.** The merged result is version 1.4.3. **Retest new version** reruns the same locked plan and shows before and after, exactly as in section 2. Retest itself is unchanged from phase 2. It does not wait for the merge: it can be pressed before or after. After the merge, Fixes also offers **Retest now**, which does the same on the merged version; before and after show in Evidence Lab.

Also decided in phase 3a:

- **What the proof runs.** Only our own demo components may run (`CLAUDE.md`, Safety). So the app first checks, byte for byte, that the changed code is identical to one of our registered demo components (in 3a, the bundled `acme-sign` 1.4.3), and then runs that registered component, never the changed file itself. If it is not identical, nothing is run and the change is not offered. Say so in the fix's Technical details and in `docs/LIMITS.md`.
- **One fix template.** There is one fix template, for one kind of bug (the missing range check), written for `acme-sign`'s code.
- **No new dependency.** The app reads and writes the repository in git's standard format itself, so the demo machine doesn't need git installed.
- **Evidence.** Download evidence also holds the change, the proof, the approvals, the merge and the code each run ran on, so the evidence fingerprint shown on the pull request can be checked.
- **Fixes come from more than one source.** Each fix records where it came from, and the Fixes list shows it. In phase 3a that is the failed tests it answers; one fix can answer several (the range check answers Official test vectors and Bad signatures). From phase 3c a fix can also come from a developer's change. A text-only suggestion is a fix too, with the status **Text only**.
- **Built to be reused.** The repository, branch, change and proof code is general, not tied to the 1.4.2 fix. It works on any commit of a connected demo repository. A change is a branch plus the commit it starts from, whoever made it. The proof reruns the locked plan on the code the change holds, through the same runner and reviewer, and only after the byte-for-byte check above has passed (nothing else ever runs). Only the fix template knows about 1.4.2 and the range check. Phase 3c reuses the same demo repository, branches and proof.
- **Which code a result ran on.** Every run records the code it ran on: the component and its version and, when the code came from the repository, the branch, the commit, and the fix or change it belongs to. Evidence Lab shows this with each result (in the run record and in the before and after headings, for example "After: acme-sign 1.4.3, the merged fix" with its commit), and the download includes it.
- **The demo code drops its giveaway comments (planned for the 3a build).** The comments in `acme-sign` 1.4.2 that point at the bug are removed: "DELIBERATELY FLAWED" in its description, the "PLANTED BUG" lines, and the two maths comments in the signature check that explain how r = 0, s = 0 gets through. The bug itself stays. 1.4.3 loses the same comments and gets the same description, so the two files differ only by the fix and the suggested change shows only the real fix: the range check plus the version line (3 lines added, 1 removed). The **Demo data** labels and `docs/LIMITS.md` keep it honest. Comments change no behaviour, so no answer in `demo/expected.json` changes: the accuracy check on a copy without them matched all 15 answers (13 November 2026, demo mode).

In phase 3b the co-pilot can explain a suggested change and offer **Open pull request** as a confirm card, but every step also has its own button.

## 7d. Migration plan (phase 4a)

Approved by Kevin on 14 November 2026, with the mockups shown then.

1. **Status, measured.** For every server: **Classical**, **Hybrid** or **Post-quantum only**; for every signing program what it signs with today (for example "ECDSA P-256, Classical"). Never a guess: **Couldn't check**, with the reason, when it can't be measured.
   - **A server measurement** makes at most about 30 handshakes, one at a time: three hellos with no key attached (one offering only hybrid key exchanges, one only ML-KEM by itself, one only classical ones), each stopping at the server's first answer; one full handshake by a classical-only client; one full hybrid handshake by the built-in OpenSSL where the server offers it; and a control, the same hellos against a hybrid and a classical test server started for the run. In isolated mode the pinned OpenSSL 3.5 container adds a full hybrid handshake as an independent check.
   - **Hybrid** only when the server asked for a hybrid key exchange or completed a full hybrid handshake; the row also says whether a classical-only client still connects. **Post-quantum only** when it accepted ML-KEM by itself and refused the hybrid and the classical hello. **Classical** when every post-quantum attempt got a TLS refusal and a classical handshake completed. **Couldn't check** for anything else: no answer, a dropped connection, a time-out, an unclear error, an unconfirmed address, or a control that was misread. Silence is never read as Classical or as Hybrid.
   - **A signing program** is measured as Verify does: its `info` command and one sign-and-check round trip confirmed by an independent library. A program that is not ours reads Couldn't check.
   - Each measurement is written down and locked before it runs, keeps its raw record and is decided by the separate reviewer, like a test.
2. **Cost, measured.** Sizes are read from real handshakes (key share each way, first message, certificate key, handshake signature); time is the median of 10 classical and 10 hybrid handshakes taken in turn. Where the server doesn't offer hybrid, that column shows published sizes (FIPS 203, FIPS 204, kept as a config value with their sources) and numbers labelled "measured on our test server". Compatibility is the classical-only client's handshake. For a signing program: its own bench against ML-DSA-65 on the reference library ("reference, not production").
3. **Four options for each system:** **Keep classical for now** (always with a review date, never "forever"), **Hybrid** (its costs said plainly: two algorithms, two sets of keys, bigger messages, more to maintain), **Full post-quantum** (every connected system must support it; no classical fallback) and **Wrap the connection** (a gateway or network encryptor for systems that can't be changed; no vendor named; it protects the connection only, not crypto inside the application, so it doesn't apply to a signing program). Each shows its cost, its blockers and three plain counts: algorithms, key sets and libraries to manage. No scores. An option that would be a step back is shown but can't be chosen, and says why ("Doesn't apply"): a system that is already Hybrid is not offered Keep classical or Wrap, and one that is already Post-quantum only is offered nothing else.
4. **A blocker is only something that must be fixed before the change** (an old library, TLS 1.3 off, a certificate below the NIST minimum). Turning hybrid on is the change itself, not a blocker.
5. **A recommendation from fixed rules** (no AI model), first match wins: Couldn't check → none; Post-quantum only → Full post-quantum, already in place; Hybrid → Hybrid, already in place; Classical and can't be changed → Wrap the connection when long-lived or internet-facing, else Keep classical for now; Classical and long-lived → Hybrid; Classical, short-lived and internet-facing → Hybrid; Classical, short-lived and internal → Keep classical for now. A signing program: long-lived → Hybrid (sign with both), short-lived → Keep classical for now; Wrap never applies. Full post-quantum is never recommended for a system that isn't already there, because the app can't measure the clients; the user can still choose it. Defaults, shown as "assumed": Long-lived; Internet-facing for a public address and Internal otherwise; can be changed. The NIST IR 8547 dates already in the app (deprecated after 2030, disallowed after 2035) appear in the reasons and cap the review date. Every recommendation states its reasons and links to the evidence.
6. **The user's choice** is recorded with its reason and time and is never overwritten. If the recommendation later differs, both show. A new choice is a new record; the earlier ones stay and are listed. If a later measurement makes a choice impossible (the choice was Keep classical and the system now measures Hybrid), the roadmap goes back to the recommendation and the choice stays in the record.
7. **Roadmap.** Each system's plan is the user's choice, or the recommendation until they choose (marked as such). Since phase 4b each track is placed by itself (point 9). (Phase 4a's single place per system, for the record: **Already there:** the plan is measured in place. **Phase 1:** going hybrid or post-quantum, internet-facing and long-lived, with no blocker. **Phase 2:** every other system going hybrid or post-quantum, with its blockers. **Later:** kept classical, with review dates. **Wrapped:** shown separately. **Not placed yet:** the status couldn't be measured. It updates when a choice, a setting or a measurement changes, and goes into the evidence download and the report.
8. **Into Fixes.** (Since phase 4b each entry is the system's change: point 10.) In phase 4a, as text-only suggestions: For each system whose plan is not yet in place: the how-to for the change itself (for example the exact setting that turns hybrid key exchange on) and one suggestion for each blocker (for a signing program the blocker's suggestion carries the steps, so it has one entry, not two). Every configuration line says whether it was checked on real software, and on which, or that it was not. An entry closes when a new measurement shows it done. The app never changes anything by itself.

### Phase 4b: make it real (points 9 to 13)

9. **Two tracks and a target.** A server has two statuses: **key exchange** (Classical, Hybrid (interim), Post-quantum only) and **authentication** (its certificate key and the algorithm it signs the handshake with: Classical when both are classical, Post-quantum when both are ML-DSA, anything else Couldn't check). A signing program has one track: its **signatures**. The target is post-quantum on every track; hybrid is an interim step, never the end. Each change is also its system's entry in Fixes, which closes ("In place (measured)") only when a new measurement shows the change in place.
11. **Try on a test copy.** One click starts a copy of the server with the change, isolated on this computer, and runs the system's own locked measurement on it. For the demo test servers the copy is the same test server with the new settings; in isolated mode the change's exact nginx lines are also applied to real nginx, checked by `nginx -t`, and measured. Before and after show side by side. The separate reviewer reviews each run; a fixed rule says whether the try passed (every copy measures what the change promises, with the controls right). Where no copy is possible (another company's server, or no settings known), the button is off and says what would be needed; in demo mode the real-nginx column says it needs isolated mode.

After Apply the app measures again by itself; if the result doesn't match the try, it says so plainly and offers Roll back. Roll back is always there after an Apply, one click, and measures again after. An applied change stays in force until it is rolled back, also when the same file is imported again: Import says so, and that import's Fixes step lists the change with its Roll back. In this version Apply works only on our own servers: the demo test servers, the lab nginx of `demo/lab-nginx.csv` (isolated mode) and the Acme Pay demo server (section 7c). For any other server Apply is off and says it needs a connector to that server, which comes in a later phase; Download change stays available. Every step (try, approvals, Apply, the measurement after, Roll back) goes into the signed evidence and the report.

## 7e. Dependency readiness (phase 4d)

The rules the answer key `demo/expected-dependencies.json` relies on, in one place.

1. **Three questions, asked of every library:** ML-KEM-768 key exchange (key pair, encapsulate, decapsulate); X25519MLKEM768 hybrid TLS (complete that handshake), asked only of TLS libraries; ML-DSA-65 signatures (make and check one). A question that does not fit the kind of library (its roles in the knowledge base: `tls`, `key_exchange`, `signatures`) reads **Doesn't apply**.
2. **Labels.** Every yes or no carries exactly one: **Release notes say** (a lookup in the knowledge base; never a pass, never shown as measured), **Measured on a public copy** (the same public version ran in our sandbox with its controls, and the reviewer decided), or **Measured in your environment** (Level 3: defined in the code and the evidence format, never produced in this phase; a test checks that).
3. **A lookup (Level 1)** says **Yes** from the version an official source names as the one that added the capability, and **No** only below that version, from the same source. If no official source names the version, there is no claim. Without a yes or no, the answer is, in this order: **Not in our knowledge base yet** (no file); **Needs your environment** (its file says only a test on your copy can answer, for example BoringSSL); **Doesn't apply**; **Couldn't tell the version**; **Not in our knowledge base yet** (no official source for this question). Each comes with its reason.
4. **Reading a version.** A distribution's package is read as its upstream version (backports bring fixes, not features): an epoch (`1:`), a `v` or `go` prefix, a `+build` part and a `-` or `~` distribution revision are dropped, so `3.0.22-1~deb12u2` reads as 3.0.22 and `3.5.9-r0` as 3.5.9. A pre-release, a commit id, `devel` or anything else that is not plainly a released version reads **Couldn't tell the version**, never a guess. A component is found by its package address (purl, without version and qualifiers) and, only when it has none, by a bare name listed in its file.
5. **A measurement (Level 2)** is the capability check: a locked test (kind `capability`) kept as a hidden plan item, run through the job runner, written to a run record and reviewed by the separate reviewer, like every test. It asks the library's pinned public copy each question in its own locked-down container, and asks the same of two control copies: **OpenSSL 3.5.9** must do all of it, and **OpenSSL 3.0.22** (Debian's build) must refuse all of it in its own words and still complete an ordinary handshake. The hybrid question is measured only on copies with a TLS client (the two OpenSSL copies), against the app's own test server that accepts only X25519MLKEM768. **Yes** only when it did it and the app's reference library agreed; **No** only when the library itself refused (its words are kept); anything else is **Couldn't check**, with the reason. A control that does not behave makes the run **Couldn't trust this run**. A measured answer replaces the lookup; where they differ, the row shows both and says the measurement counts. When the copy is itself one of the controls, the result says so. In demo mode every measurable row reads **Couldn't check (needs isolated mode)**; lookups still work. The check and the reviewer never ask where the library came from: the target (one small interface; only the public pinned copy exists) is the only thing Level 3 adds.
6. **Top entries and tying.** A top entry (a group heading) is the thing the list describes, anything the list marks as an application or a container, and any component whose name and version equal a signing program of the imported file, which is tied to it automatically ("tied by name and version"). Top entries are the customer's own software and are not looked up. Every other library belongs to the nearest top entry above it (on a tie, the one first in the file), with the path it came through ("through python 3.12.3"). **Part of** ties a top entry to one system of the file, or none; the person's choice wins over the automatic one. An untied entry's libraries are answered and block nothing. Entries that are not libraries (an operating system, files) are counted, not looked up.
7. **Blockers.** Only a **No** on a library tied to a system blocks: a server's **key exchange** track by a TLS library that can't do X25519MLKEM768; its **authentication** track by a TLS library that can't do ML-DSA-65; a signing program's **signatures** track by a signatures library that can't do ML-DSA-65. A blocker is named on the track ("It relies on openssl 3.0.22 (through python 3.12.3), which can't do …", with its label and the first version that can) and on the roadmap. It is something to fix before the change, so the band follows today's rule (section 7d). A library with no yes or no is a thing to check, never a blocker. Key exchange stops Hybrid and Full post-quantum; authentication stops Full post-quantum; signatures stop both.
8. **Fixes.** One Text only entry for each library and system it blocks: "Update *library* to *version* or later", with the official source, quoted. It offers no code change and no pull request: it is other people's software.
9. **Evidence.** The file gets a `dependencies` part (the list, every answer with its label and the source of every lookup, the ties and blockers, and each measurement with its locked test, run record and review); the report gets part 7, "Dependencies".

## 7f. Otto in Evidence Lab: advisories, test packs and the loop (phase 5c)

Approved by Kevin on 17 November 2026 with the phase 5c plan and three changes of his own: Otto uses Claude, Otto proposes the fix, and a Codespace setting. The rules, in one place. Section 2 has the screens, section 3 the harness and Otto's use of Claude, section 7 the advisory check.

1. **The loop.** A newly published weakness becomes a locked test; the runner and the reviewer the app already has decide whether a program is affected; a fix is proven on a copy; a person approves it; and the same tests run again after every change. Otto designs the test and keeps the record. Every result still comes only from the runner and the reviewer. In this phase the loop covers **signing programs and libraries only**; servers follow in phase 5d.
2. **Two sides, and what crosses.** Otto's research side (`backend/ottolab/`; a build step on our own machine, which in production would run at Isogeny Labs) turns published advisories into tests and ships them as signed, versioned **test packs**. The customer's side is the app. Only a signed test pack crosses from research to the customer, and only a signed evidence file leaves the customer. The app never imports the research side, the research side has no way into an assessment, and the app needs neither the research side nor a model to run.
3. **The snapshot.** Research starts from a dated snapshot of real published advisories (section 8): for each one its id, its package, the date it was published, and pieces of its official text copied word for word, each with the page it came from, the date it was read and a SHA-256 of the downloaded bytes. It is data.
4. **Three Claude steps for each advisory, each checked before anything uses it.** *Read the advisory:* the weakness in plain words, the affected versions and the publisher's fixed version, each tied to a quoted line; a quote that is not in the publisher's text, character for character, is refused. *Design a test:* a design note that picks published cases for the one building block of this version ("run these published signature cases") with its control and its pass rule, or "no test fits" with the reason; a design is data and can't carry code. *Propose a fix:* only the publisher's own fixed version, with the quoted line that shows it. Claude is told not to rate how serious a weakness is, and an answer whose own sentences use a word this app never says about a system ("secure", "score", "severity", "critical") is refused.
5. **Tried before it ships.** Before a test enters a pack, Otto's harness runs it on public copies as an experiment registered in advance: the app's reference library as the baseline, the affected version, the publisher's fixed version, and the accept-everything control that must fail, with a numeric prediction and a kill line frozen before the first run. The numbers come from Evidence Lab's own lock, run and review path; the harness judges them against the frozen thresholds; and the runs are then replayed in a separate step under a second author's name. That second author is a second role of the same build on the same computer, not an outside party, and the screens say so. A test reads **Test ready** only if the affected version got at least one selected case wrong, the fixed version got as many right as the reference library, the control got every must-reject case wrong, and the replay gave the same numbers. A design that fails its own trial reads **Not offered** and stays out of the pack. An advisory that no building block can show reads **No test yet**, with the reason. So does an advisory whose design selects exactly the published cases of the check of another advisory **about the same library**: that would be the same check under a second name, which could not tell the one weakness from the other, so it is refused before any trial and no test is registered. Only a check that exists counts: a test of an earlier pack, or a design of the same build whose own trial held. A design that was never tried or that failed its trial is no check, and the same cases for another library are another check, tried on that library's own versions. The pack builder looks once more before it signs, and signs no pack that would hold the same check twice.
6. **A library's fix** ships with its advisory's test: the publisher's fixed version with its quoted source, labelled **From Otto**. It is called **proven** only if a second registered trial shows that, on public copies, the advisory check passes on the fixed version **and every other locked test passes there too** (the Independent exam, Attacker tricks and every advisory check that held its own trial). This is read strictly: a test that still fails on the fixed version, for whatever reason, makes the fix **not proven**, and the pack says why. Speed is not part of this trial: timings hold only for the computer they are measured on. A fix is proposed only for the library its advisory names: when another program fails the same check, Fixes says that the test pack holds no fix for that program. The app writes no code change and no pull request for other people's software. **Two proof rows (18 November 2026).** Wherever a library's fix appears (Fixes, Evidence, the report, the signed evidence) it says two things apart, in the same words. "Proven on public copies" is the pack's own trial: **Passed** when the fix is proven by the rule above, and otherwise **Not proven** with what the trial showed (for Java: "17.0.2 fails the advisory check and 17.0.3 passes it, but another locked test still fails on 17.0.3."). "Proven on your system" is this assessment's own retest on the fixed version: **Not yet** ("Update the library, then press Retest.") until there is one; then **Passed**, with its date and a link to the run, only when the advisory check and every other pass-or-fail test the plan holds for that library has a result in that same retest and passed (the Independent exam, Attacker tricks and every advisory check; speed is left out, as in the trial); **Not proven**, with what did not pass, when one of them has a result there that is not a pass. While that retest is still running, or after it was interrupted with some of those tests left without a result, the row stays **Not yet** and says how many have a result: half a retest proves nothing. Both rows repeat records: the pack's counts and the reviewer's results.
7. **A change for your own code.** When an advisory check has failed on the assessment's own program, Otto writes the code change (the fourth Claude step) through the same engine socket the fix template uses, from the advisory, the cases the program got wrong and the program's source file. The answer is a list of exact line edits, and nothing in it is run. It is offered only if it applies cleanly and the program it gives is, byte for byte, one of our registered demo programs (only those may run). It is then labelled **Written by Otto** and takes the path of section 7b unchanged: a copy on a branch, the proof that reruns every locked test, the separate reviewer, a person's approval and merge. Otherwise it is not offered: where the fix template answers the failure, Fixes offers the template in its place and says why in one plain sentence, and the refused step is kept in the assessment's Otto ledger when the person connects the code; where no template answers it, Fixes lists the failure and says that no change is offered. With Live Otto on and a key present, the answer comes from Claude and not from the recorded answers: until a person connects the code, the fix is listed as **Not written yet** (never as written by Otto), and its card says what the click sends and that an answer which is not one of our registered demo programs is refused although the request was made on the key. When no advisory check has failed, nothing changes: the fix template answers as before. **Since 18 November 2026 (Kevin's decision)** the program that Otto's recorded change for `acme-sign` gives is itself a registered demo program, `acme-sign 1.4.3-otto` (section 8). So on the demo Otto's own change is offered: as a proposal (point 9) that a person accepts before **Connect demo code** can be pressed; it is then proven on that program, approved, merged and retested like any change. A retest can choose that program only after its change is merged in that assessment. The fix template is the fallback: where the Otto harness is not installed (a decision on the proposal could not be recorded, and Fixes says so), and where Otto's answer does not give a registered program. What stays out of this version: running a program that Claude wrote and that is not one of the registered ones.
8. **A test pack is data, signed.** One JSON file in the evidence file's envelope (`pack`, `fingerprint`, `public_key`, `signature`; Ed25519). It holds the advisories with what Otto read in each, each test's design and its trial, each fix and its trial, every Claude step with its answer, and the fingerprints that tie it to the snapshot, the pinned Otto commit, the research scripts and the research ledger. Nothing in a pack runs. The app takes a pack only when its signature holds, its signer is a key this installation trusts, its shape is exactly the known one, every design in it can be run by this version, and it follows the installed pack (each pack names the fingerprint of the one before). Anything else is refused with one plain sentence. Packs install in order and are never removed. **Check for updates** looks only in the updates folder on this computer: in the demo, the packs shipped in `research/packs/`. A pack built on this computer by the research command goes into the data folder's own updates folder, is signed with a key made on this computer, and is shown as made here.
9. **Otto proposes; a person decides** (rewritten on 18 November 2026 from Kevin's acceptance criteria of that day). Everything Otto produces for an assessment arrives as a proposal labelled **From Otto**, with **Accept** and **Reject**: a check (decided on Advisories), a fix (Fixes), a change to the migration plan (Migration, Systems) and a dependency update (Dependencies). Each proposal is decided by itself; there is no button for several at once.
   - **Reject** asks for an optional short reason (one line, 300 characters at most). A rejected proposal is never deleted: it stays on the record as "Not added (*reason*)" and can be taken up again with **Reconsider**.
   - **An accepted proposal can be undone until it has run or been applied:** a check until it has a run; a change to your own code until the code is connected; a library's update until a retest on the updated version is running or has run; a plan change until a newer result of its check has passed. After that the accept stands, and the button says why.
   - **Accepting, rejecting, undoing and reconsidering run nothing** and change nothing on any system. Running a check, connecting code, approving, merging, applying and retesting stay their own clicks, as before. Nothing is added, run, applied or merged by itself, and there is no timer: tests rerun on a click, and where the app already reruns by itself (fix proofs and retests).
   - **Where the proposals come from.** A proposed check: each ready test of the installed, signed test packs, for each signing program of the file it fits. A proposed fix: the pack's update for the library its advisory names, or Otto's change for your own code (point 7). A proposed plan change and a proposed dependency update: rules over the results, with no Claude step (Claude's jobs stay the four of section 3). Proposals are worked out each time a page is read and are never stored; only a person's decisions are stored. A proposal that a person's decision stands on (accepted or rejected) and that Otto would no longer make stays on the record, marked as no longer proposed; one that is open (never decided, or open again after an undo or a reconsider) is simply no longer proposed, and the decisions made on it stay in the record and in the evidence.
   - **Who and when.** Every accept, reject, undo and reconsider is recorded with the time and with the name the app already records for approvals ("You"); the app has one login and says so beside every list of decisions. The record is in the database (append-only), in the assessment's Otto ledger (point 10) and in the signed evidence (point 11).
   - **Results are untouched.** A proposal and a decision word no result and decide none. Results still come only from the runner and the reviewer.
   - **A new pack** starts the loop again: after it is installed, Otto proposes the checks it brings for each open assessment's file, and the Overview and the Project overview say how many wait.
   - Installing a pack stays a person's click, and **Live Otto** can be switched off at any time; the app then works on the recorded answers and says so.
10. **Two ledgers, kept with Otto's harness.** The **research ledger** (`research/lab/`) shows that each test and each fix was registered, tried and judged before its pack was signed; a pack names that ledger's latest entry. The **assessment's Otto ledger** (one for each assessment, in the data folder) gets a lock entry when an advisory check is added, written before the check can run, and one entry for each reviewed run of that check (a first run, a retest or a fix proof), which binds the run and its review to the locked test and names who proposed and who reviewed. It also keeps every Claude step taken in the app. Since 18 November 2026 the lock entry is written when a person accepts the proposed check, and the ledger also gets, for each proposal a person decides on, one entry that names the proposal (written with the first decision on it) and one entry for each decision: accept, reject, undo or reconsider, with who, when, the reason, where the proposal stood before and after, the decision's number, and the SHA-256 of the proposal as it stood. Otto's harness runs a pinned checker of ours on each run entry and each step entry, and a second pinned checker of ours on each decision entry (`backend/app/otto/checker/decisions.py`, beside `recheck.py`, which is unchanged so that earlier ledgers and evidence files read as before): it checks that the entry is whole and that the step is one the app allows from where the proposal stood. Its answer is a check of the record, never the decision itself and never a result. What the ledger confirms is **binding**: that a run belongs to a test locked earlier, and that the reviewer was not the proposer. It holds no result, and its verdict is never shown as one. Evidence Lab's own read gate still redoes every review each time a result is shown.
11. **Evidence.** An assessment with an advisory check, a Claude step or a decision on one of Otto's proposals gets an `otto` part inside the signed evidence: the pinned harness, the signed packs its checks came from, each advisory check with its lock entry, the assessment's ledger with the hash of its latest entry, every run the ledger binds, every Claude step, and since 18 November 2026 `proposals`: every proposal of Otto's in the assessment, decided or not, as it stands, with each decision on it (what was decided, by whom, when, the reason, the copy of the proposal it was made on with its SHA-256, and its entry in the ledger). A fix from Otto carries its proposal, and a library's fix its two proof rows. The report gets part 8, with a table of the proposals and the decisions on them. The verify command holds the decisions in the file and the decision entries in the ledger to each other, one for one: the same fields, an order the app allows, the SHA-256 of the copy decided on, the pinned checker's acceptance, and no decision in the ledger that is missing from the file. A proposal may stand as accepted with no decision only where the file holds the check it stands for (one added before decisions were recorded); the word shown for where a proposal stands must be the word of that state; and a proposal Otto no longer makes must read as its last decision was made on it. An entry the pinned checker did not accept is an attempt, not a decision, and the command says so. A decision is shown to the pinned checker before anything is written, so a refused one leaves the ledger, the database and the plan as they were. What the ledger knows nothing of is a proposal nobody decided on: that part of the file is covered by the file's own signature only. One command checks all of it, `python -m evidence verify file.json`: after the file's own signature it checks the packs' signatures, each check's design and lock entry, the ledger's chain, the runs it binds and Claude's steps, and then runs Otto's own audit. A ledger read from a file is data, and nothing it names is ever run. Asked to check entries again, Otto's harness would start the verifier an entry names, and it finds that entry by its id without asking what kind of entry it is. So the harness is never asked to. First, every entry must be in the exact form this app writes: one of three kinds, with exactly the fields of its kind, an objective that names this app's own pinned checker and nothing else, and each pointer leading to an earlier entry of the right kind. A file that fails this fails the check, and nothing is run. Then the harness audits the chain and the records without running any verifier, and the app itself runs its own pinned checker again on every checked entry and compares the answer with the stored one. A run in the file that the ledger does not bind, and an entry that could not be checked again, fail the check too. A run that the file's own list of tests shows must be the very run the ledger binds: its record and its review must match the SHA-256 the ledger holds, not only its number. A file that holds an advisory check and no Otto part does not verify. A ledger longer than any assessment's, or one that settles the same entry twice, is refused, and checking again has a time limit, so a file made to be slow can't hold the command for hours. With `--previous`, the two files must be signed with the same key. Text from the file is printed with anything that is not a plain printable character taken out. With `--previous OLDER.json` it also checks that the older download's latest ledger entry is still in the chain, so history can't be cut or rewritten between two downloads without the check failing (entries added after the older download are not covered by that comparison). Where the Otto harness is not installed, the command still makes its own checks, says that Otto's audit was not run, and ends with the "not confirmed" code. That is not a pass.
12. **With Otto and without it.** The four earlier answer keys must match exactly with the harness installed and with it missing. Without it the app works as before and says why (section 2).
13. **Wording.** Advisories, the packs and Otto's records never word a result of their own: they repeat the reviewer's words. A quoted line is shown as its publisher's, tagged "quoted from the named source, not a result", with the source's name, its publisher and the day it was read; its link opens the address the text was read from (for a file in a repository, the file at its pinned commit). The quote is not always from the advisory page: where the advisory does not put the weakness into words, the reading quotes the publisher's own source file. What Claude noted while reading is shown folded, labelled as Claude's words and as information. A count of results never counts a program that has no result yet. No "secure", no score, and nothing about how serious a weakness is. **Since the 5c fixes (19 November 2026) no sentence says what Otto did** ("Otto wrote", "Otto proposes", "in Otto's words", "Why Otto proposes it", "Otto found", "Otto has", "Otto's proposal", "Otto asked", "Otto no longer"): a sentence says what is proposed or written, in short sentences, one idea each ("A change was written for CVE-2022-21449 (Missing ECDSA signature range check). What it changes: …", "Why it is proposed", "When a newer result of this check passes, it comes off the to-do list. It stays in the history."). What stays: the tag **From Otto** on every proposal, **Written by Otto**, **Not written yet**, **Live Otto**, **Otto in this project**, the harness and "Otto is not installed" lines, "Otto ledger entries", "No recorded answer: this needs Live Otto.", "Otto has no say in any result.", the statuses and the titles; Claude's own writing is labelled once. A test reads every sentence the code can show and fails on the phrases (`backend/tests/otto/test_wording.py`). Nothing recorded is reworded: a decision keeps the copy of the proposal it was made on, with its SHA-256.
14. **Otto researches by itself (phase 6, 19 November 2026; Kevin's priority for the overnight run).** Nobody installs a test pack to get new checks. On Advisories a person presses **Look for new advisories**, then **Design and prove tests** (section 2).
   - **The source.** One public source, OSV (`https://api.osv.dev/v1/query`), asked by a person's click only. One request for each library the assessment names that the source keeps by name (packages of npm, PyPI, Go, Maven, crates.io, NuGet and RubyGems). The request holds the package's name and its ecosystem and nothing else: no version, no address, no file, no key. The answer is data: it is held to the shape the source documents, a record that does not fit is left out and counted, and no rating of how serious a weakness is read from it. A folder of recorded answers can stand in for the source (`EVIDENCE_LAB_ADVISORY_SOURCE`); tests, the end-to-end walk and the GitHub checks use that and never the network.
   - **Which advisories fit.** Whether an advisory names a version this assessment has is worked out on this computer, from the version ranges the record gives. Where a version can't be read, the block says so and guesses nothing.
   - **When a test can be tried.** Only for a library this version of the app has pinned public copies of, in an affected and in the fixed version, and only in isolated mode. Otherwise the advisory reads "No test yet" with that reason, and Claude is not asked about it.
   - **The research run** is the research side's own command (`ottolab.build next`), started by the click as a separate process: the app still never imports the research side. For each advisory it takes the steps of points 4 to 6 (read, design, try on public copies as an experiment registered in advance, replay by a second author; then the publisher's fixed version as the fix, with its own trial). With Live Otto off it uses only the answers recorded during the build; an advisory with none stays open, reads "No recorded answer: this needs Live Otto.", and can be tried again. With Live Otto on, Claude is asked within the spending limit per run, and what is sent is the advisory's published text.
   - **What comes out** is a test pack as in point 8, signed with a key made on this computer and shown as made here. The click that started the run installs it, after any built-in pack that is not installed yet (packs still install in order and are never removed). This is the one case where a pack is installed without a click of its own: the box of **Design and prove tests** says so before the run starts. Its proven tests are then proposed like every pack's (point 9). A test that was not proven is in the pack too, with its reason, and is never proposed. An advisory the run could not settle (no answer came, or its trial on public copies did not finish) is left out of the pack: nothing is signed about it, the block says why, and a later run can take it up. A run that settles nothing makes no pack. The click installs only the pack its own run made; a pack made here that was never installed is installed by a person in Settings first, and the block says so. One run at a time; a run still going after four hours is ended.
   - **The record.** Every look (when, by whom, the source, the names sent, what was found and what was left out) and every research run (its start, its end, the advisories, whether Live Otto was on and its limit, the packs installed first, the pack it made, what the command printed) is kept add-only. The proof itself is in the pack and in the research ledger of this computer, exactly as a shipped pack's trial is. The signed evidence holds the looks and the runs of the assessment, and the verify command checks them and that a run's pack is in the file.
   - **What it covers, said plainly** in the block and in `docs/LIMITS.md`: libraries published on those seven ecosystems, by name; a test only where pinned public copies exist (of the libraries the source keeps by name, today python-ecdsa and elliptic, in the versions pinned in the app) and only from published test cases the app can run today (ECDSA P-256 signature checks). With today's pinned versions most newly published advisories read "No test yet". The two shipped packs stay as the built-in starting set.
