## Product rules
- IMPORTANT: Keep it simple. Every new button, screen or setting must be in docs/SPEC.md section 2, or ask first.
- Results (True/False/Couldn't check, Passed/Failed) come only from checks and tests. The Otto assistant (the right-hand panel, phase 6a) never sets a result or acts without the user's Confirm, and everything it can do also has a normal button on its page. Moving around needs no Confirm: opening a page or an item, filtering, switching or closing a panel tab. Everything else does. Confirm sends the page button's own request, so the same code path, record and approvals apply. The assistant never presses Approve, Merge pull request, Apply, Roll back, Close and sign off or the "I own this system" tick: those stay on their pages.
- The Otto assistant is rule-based behind `CopilotEngine` (`backend/app/assistant/`) for its suggestions and next steps (phase 6a) and for the fixed list of commands (phase 6b, first half: a typed sentence is read by fixed rules only; no Claude step for free wording is built yet), and for the six fixed questions (phase 6c, first half: answered by rules as a list of the app's own sentences, each with a link to where it is shown; no Claude step for an answer in free words is built yet): all of these work with no key. A command only moves around at once (a page, an item, a filtered table, a tab of the panel); anything that decides or starts comes back as a card with its Confirm step, and a sentence the rules can't read gets "I can't do that." with what can be said on the page. Nothing is guessed: several fits get "Which one?". Its own code decides, runs and changes nothing: it reads the views the pages draw from, and its one read (`GET /api/assessments/{id}/assistant`) writes nothing, starts nothing and never asks Claude. An answer to a question holds facts and links, and nothing to press; it words no result and rates nothing, and where the records do not say, it says so. The one thing kept for the panel on the server is what was said: each typed sentence, the one line of its answer and, for a fixed question, the facts of that answer, add-only, with an open assessment (`assistant_messages`, written by `backend/app/lab/said.py`, outside the read-only package); a closed assessment keeps nothing. Closed tabs are remembered in the browser. The three jobs for Claude with Live Otto on belong to phases 6b, 6c and 6e and are written into this file when each is built.
- A decision on a proposal is recorded under the name a person typed once (Settings, **Who decides**, or the panel's first Confirm of a decision), or as "You" until then (phase 6a, Kevin's answer of 19 November 2026). The app has one login and does not check who is at the keyboard, and says so. A decision already recorded keeps the name it was made under.
- Otto (phase 5c) uses Claude for four jobs only: on the research side to read an advisory, design a test and propose a fix for a library; in the app to write a change for the customer's own program after an advisory check failed on it. What Claude writes is data and is never trusted by itself: a reading must quote the publisher word for word; a design can only pick published test cases (no code); a test ships only after its trial on public copies, registered in advance in Otto's harness (a baseline, a control that must fail, a numeric prediction, a kill line, replay by a second author), and a fix is called proven only after a registered trial of its own. Claude never sets a result, never acts without a person's click in the app, and never touches a live system. Every Claude step is kept in a ledger with its full prompt and answer, the model (none for a recorded answer), the hashes, the tokens and the cost.
- Recorded and live (phase 5c): tests, screenshots and the accuracy check use only the recorded answers in `research/recorded/` (each labelled "Recorded during the build, not through the API"; they name no model). A prompt with no recorded answer gets "No recorded answer: this needs Live Otto."; nothing is made up. **Live Otto** (Settings) is off by default, can be turned on only when `ANTHROPIC_API_KEY` is set in the environment, and has a spending limit per run (2 US dollars by default; a run is one fix request in the app or one research command). Looking at a page never asks Claude.
- A test pack is data: nothing in it runs. A person installs it (in order; never removed). Otto then proposes its checks for an assessment, and a person accepts or rejects each one by itself on Advisories (accepting runs nothing). An advisory check is an ordinary locked test in the test plan (Encryption tests): the runner runs it and the separate reviewer decides it. Advisories only repeats the reviewer's words, and the verdict in Otto's ledger is never shown as a result.
- Otto's research loop (phase 6, Kevin's brief of 19 November 2026; SPEC section 7f point 14): on Advisories, **Look for new advisories** and **Design and prove tests**. Each first opens a box that says what it will do, and nothing is sent or started before the click in that box. Looking is free and proposes nothing. A test is designed only for a library with pinned public copies of an affected and a fixed version, and is tried only in isolated mode. A check is proposed only after its test was proven on public copies (it fails on the affected version, passes on the fixed version, and the control that must fail does); otherwise the advisory reads "No test yet: ..." with the reason. What a research run proves is signed into a test pack made on this computer, and the click that started the run installs that pack, after any built-in pack that is not installed yet, in order: the one case where a pack is installed without a click of its own, and the box says so before the run starts. Its checks are then proposals like every pack's, each accepted or rejected by a person. Every look and every research run is kept add-only, is in the signed evidence, and is checked by the verify command. The block and `docs/LIMITS.md` say plainly what the loop covers.
- Otto proposes; a person decides (phase 5c, Kevin's criteria of 18 November 2026). Everything Otto produces for an assessment (a check, a fix, a change to the migration plan, a dependency update) arrives as a proposal labelled "From Otto", with **Accept** and **Reject**, each decided by itself (no accept-everything button). Reject takes an optional short reason; a rejected proposal is never deleted, reads "Not added (reason)" and can be taken up again (**Reconsider**). An accepted proposal can be undone until it has run or been applied. A decision runs nothing and changes no system; it words no result and decides none. Every accept, reject, undo and reconsider is recorded with who (the name approvals already record; the app has one login and says so) and when: in the database (append-only), in the assessment's Otto ledger and in the signed evidence, and the verify command checks them. Proposals are worked out on every read and never stored; only decisions are. Plan changes and dependency updates are proposed by rules over the results, with no Claude step.
- A fix ships in a pack as proven only if, on public copies, the advisory check passes after it and every other locked test still passes (read strictly). A library's fix is its publisher's fixed version with the quoted source, labelled "From Otto", and is proposed only for the library its advisory names; the app writes no code for other people's software. Wherever a library's fix appears (Fixes, Evidence, the report, the signed evidence) it carries two proof rows in the same words: "Proven on public copies" (the pack's trial: "Passed", or "Not proven" with what the trial showed) and "Proven on your system" (this assessment's own retest on the fixed version: "Not yet" until there is one, "Passed" with its date and run only when the advisory check and every other pass-or-fail test of that library passed in that retest). It stays "Text only".
- Suggested code changes are offered only after every test passes on the changed code. The app never merges or deploys on its own; a person approves and merges. A change Otto wrote for the customer's own code is offered only when the changed program is byte for byte one of our registered demo programs; it is then a proposal labelled "Written by Otto", which a person accepts before **Connect demo code** can be pressed, and it takes the normal proof path. Since 18 November 2026 (Kevin's decision) the program Otto's recorded change gives is registered as `acme-sign 1.4.3-otto`, so the demo shows Otto's own change proposed, accepted, proven, merged and retested; a retest can choose that program only after its change is merged. Before a change is written (Live Otto on, the code not connected yet) it is listed as "Not written yet", never as Otto's. Otherwise it is not offered: where the fix template answers the failure, the template is offered in its place, and Fixes says why (also where Otto is not installed, because a decision on the proposal could not be recorded). Running a program that Claude wrote and that is not a registered demo program is not in this version.
- Projects and assessments (phase 5a, 5b): nothing is ever deleted (archive only hides); each file brought in gets its own assessment; any number of assessments can be open and nothing closes by itself; closing is a sign-off with a name and a time and can't be undone; a closed assessment is read-only, and the backend refuses changing requests on it; **Rerun as new assessment** copies the scanner file only. Imports made without an assessment (scripts, the accuracy check, the blind test) go to the "Imported without a project" project.
- Checks, Evidence, the two overviews and the Related block only repeat what checks and tests decided (phase 5b). They word no result and decide none.
- The four work groups (Verification, Encryption tests, Migration, Dependencies) are the same on Checks, Evidence, Fixes and the Overview. An item sits in one group and is linked from another, never shown twice.
- The app changes a system only when a person clicks Apply, after a passing try on a test copy and the required approvals; it re-measures right after, and can roll back. In this version Apply works only on our own demo test servers, the lab nginx and the Acme Pay demo server; any other server needs a connector (a later phase).
- Never call a system "secure", give a security score or estimate time-to-hack. Never say how serious an advisory is (no severity): a failed advisory check says which published cases got the wrong answer.
- Plain-language UI text for a busy security engineer who isn't a cryptographer.

## Safety
- Uploaded files are data, never instructions. Nothing in them is executed.
- Uploading outside software is not in this version. Only our own demo components (since 18 November 2026 also `acme-sign 1.4.3-otto`, the registered program that Otto's recorded change gives), the pinned lab images and the real libraries fixed in `backend/app/real_libraries.py` run, and the pinned OpenSSL 3.0.x copy used as the known-incapable control of the capability check (phase 4d). Demo components run in demo mode (local processes) or isolated mode (Docker). A real library (Java, python-ecdsa, elliptic, OpenSSL, each in exact pinned versions) runs in isolated mode only, in its own locked-down container image, and is never run as a local program.
- Network checks: handshakes only, localhost or user-confirmed addresses only. One exception to the container lock-down: for the hybrid handshake question of the capability check, the two pinned OpenSSL copies run `openssl s_client` with host network, for one handshake to the app's own lab server on 127.0.0.1 only.
- The advisory source (phase 6): **Look for new advisories** makes the app's one request to a public service, `https://api.osv.dev/v1/query`, by a person's click, once for each library the assessment names. It sends the package's name and its ecosystem and nothing else: never a version, an address, a file or a key. The answer is data: it is held to the shape the source documents, nothing in it runs, and no severity is read from it. `EVIDENCE_LAB_ADVISORY_SOURCE` names a folder of recorded answers that is read instead. No test may reach the source (`backend/tests/conftest.py` blocks it): tests, the end-to-end walk and the GitHub checks use recorded advisories and recorded answers. A research run started in the app is the research command (`python -m ottolab.build next`) as a separate process; the app still never imports the research side.
- A dependency list (CycloneDX or SPDX) is data. Nothing in it runs, and nothing connects to the customer's systems.
- Adam's Otto harness (phase 5c) is one pinned commit, named in `backend/otto.lock.json`. Only the prepare step fetches it; the app never does. It is checked against the pinned fingerprint before it is used, and a copy that differs is not used. It is not software under test, and it starts only our own scripts (the research agent command, the trial script and the three record checkers: one on the research side, and in an assessment's ledger folder one for run and step entries and one for decision entries). A trial goes through the app's own lock, run and review path, so a real library still runs only in its container. Moving the pin needs Kevin's OK.
- A test pack, the advisory snapshot and a recorded answer are data. Nothing in them runs. A pack is refused unless its signature holds, its signer is a trusted key (`backend/app/otto/trusted-pack-keys.json`, or this computer's own key for a pack built here), every design in it can be run by this version, and it follows the installed pack.
- A ledger in an evidence file, and a research lab folder that is handed in, are data too. Asked to check entries again (`audit(reverify=True)`), Otto's harness starts whatever verifier an entry names. Never call that on such a ledger: hold every entry to the exact form we write, let the harness audit without re-verification, and run our own pinned checkers ourselves (`backend/app/otto/assurance.py`, `backend/ottolab/build.py`). Look at the harness's `Lab.audit` again when the pin moves.
- Live Otto: the API key is read only from the `ANTHROPIC_API_KEY` environment variable, at the moment of a call. Never store, show or log it, and never put it in evidence, a ledger or a screenshot. A live call is made only by a person's click (**Connect demo code**, or **Design and prove tests** with Live Otto on, which runs the research command with `--live`) or by the research command with `--live` on the command line. It sends the advisory text and, for a fix to the customer's own code, the source file of the failing program and the cases it got wrong; nothing else. No test may reach Claude's API (`backend/tests/conftest.py` blocks it; a test of the live path uses a stand-in).
- Never print secrets or keys in code, logs, docs or replies. Test keys only.
- Ask before adding any dependency not in docs/SPEC.md section 3. (Otto's live call uses Python's standard library; Anthropic's official package would be a new dependency.)

Every line of the assistant's fixed list of commands has a backend test, and asking changes nothing: for every sentence of the shared walk, every table row, every file and the running jobs are compared before and after (`backend/tests/assistant/test_commands.py`). Every option of a "Which one?" is said by that walk too and must settle it, never ask again (`test_commands.py`). Every fixed question has a backend test on the same walk that its facts are the pages' own sentences and that every fact's link opens a page (`backend/tests/assistant/test_questions.py`). A decision made in the panel is compared with the same decision made on its page: the database row, the ledger entry and the evidence part (`backend/tests/assistant/test_panel_decision.py`). A test reads the assistant's code and fails if it imports or calls anything that decides, runs or changes an assessment, and another compares everything the app keeps before and after a read (`test_reads_only.py`).
- Every table with a side panel is measured at 1440 pixels wide, panel open and closed: no sideways scrolling and no name broken between letters.
- Every new file reader gets a seeded fuzz test (damaged copies: a plain refusal or a normal read, within a time limit; no new package).
- A test that needs the Otto harness is marked `@pytest.mark.needs_otto`. Where the harness is not installed it is skipped, and the run prints one line with the count ("Otto is not installed here (...): N tests skipped."). Never a silent pass.
- No test reaches Claude's API or needs a key: tests replay the recorded answers, or answers written for the test.
