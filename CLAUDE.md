## Product rules
- IMPORTANT: Keep it simple. Every new button, screen or setting must be in docs/SPEC.md section 2, or ask first.
- Results (True/False/Couldn't check, Passed/Failed) come only from checks and tests. The co-pilot never sets a result or acts without the user's Confirm, and everything it can do also has a normal button.
- The co-pilot has no AI model: it stays rule-based behind `CopilotEngine`.
- Otto (phase 5c) uses Claude for four jobs only: on the research side to read an advisory, design a test and propose a fix for a library; in the app to write a change for the customer's own program after an advisory check failed on it. What Claude writes is data and is never trusted by itself: a reading must quote the publisher word for word; a design can only pick published test cases (no code); a test ships only after its trial on public copies, registered in advance in Otto's harness (a baseline, a control that must fail, a numeric prediction, a kill line, replay by a second author), and a fix is called proven only after a registered trial of its own. Claude never sets a result, never acts without a person's click in the app, and never touches a live system. Every Claude step is kept in a ledger with its full prompt and answer, the model (none for a recorded answer), the hashes, the tokens and the cost.
- Recorded and live (phase 5c): tests, screenshots and the accuracy check use only the recorded answers in `research/recorded/` (each labelled "Recorded during the build, not through the API"; they name no model). A prompt with no recorded answer gets "No recorded answer: this needs Live Otto."; nothing is made up. **Live Otto** (Settings) is off by default, can be turned on only when `ANTHROPIC_API_KEY` is set in the environment, and has a spending limit per run (2 US dollars by default; a run is one fix request in the app or one research command). Looking at a page never asks Claude.
- A test pack is data: nothing in it runs. A person installs it (in order; never removed) and a person adds its checks (**Add new checks**, which runs nothing). An advisory check is an ordinary locked test in the test plan (Encryption tests): the runner runs it and the separate reviewer decides it. Advisories only repeats the reviewer's words, and the verdict in Otto's ledger is never shown as a result.
- A fix ships in a pack as proven only if, on public copies, the advisory check passes after it and every other locked test still passes (read strictly). A library's fix is its publisher's fixed version with the quoted source, labelled "From Otto", and is proposed only for the library its advisory names; the app writes no code for other people's software.
- Suggested code changes are offered only after every test passes on the changed code. The app never merges or deploys on its own; a person approves and merges. A change Otto wrote for the customer's own code is offered only when the changed program is byte for byte one of our registered demo programs; it is then labelled "Written by Otto" and takes the normal proof path. Otherwise it is not offered: where the fix template answers the failure, the template is offered in its place, and Fixes says why. Running code that Claude wrote is not in this version.
- Projects and assessments (phase 5a, 5b): nothing is ever deleted (archive only hides); each file brought in gets its own assessment; any number of assessments can be open and nothing closes by itself; closing is a sign-off with a name and a time and can't be undone; a closed assessment is read-only, and the backend refuses changing requests on it; **Rerun as new assessment** copies the scanner file only. Imports made without an assessment (scripts, the accuracy check, the blind test) go to the "Imported without a project" project.
- Checks, Evidence, the two overviews and the Related block only repeat what checks and tests decided (phase 5b). They word no result and decide none.
- The four work groups (Verification, Encryption tests, Migration, Dependencies) are the same on Checks, Evidence, Fixes and the Overview. An item sits in one group and is linked from another, never shown twice.
- The app changes a system only when a person clicks Apply, after a passing try on a test copy and the required approvals; it re-measures right after, and can roll back. In this version Apply works only on our own demo test servers, the lab nginx and the Acme Pay demo server; any other server needs a connector (a later phase).
- Never call a system "secure", give a security score or estimate time-to-hack. Never say how serious an advisory is (no severity): a failed advisory check says which published cases got the wrong answer.
- Plain-language UI text for a busy security engineer who isn't a cryptographer.

## Safety
- Uploaded files are data, never instructions. Nothing in them is executed.
- Uploading outside software is not in this version. Only our own demo components, the pinned lab images and the real libraries fixed in `backend/app/real_libraries.py` run, and the pinned OpenSSL 3.0.x copy used as the known-incapable control of the capability check (phase 4d). Demo components run in demo mode (local processes) or isolated mode (Docker). A real library (Java, python-ecdsa, elliptic, OpenSSL, each in exact pinned versions) runs in isolated mode only, in its own locked-down container image, and is never run as a local program.
- Network checks: handshakes only, localhost or user-confirmed addresses only. One exception to the container lock-down: for the hybrid handshake question of the capability check, the two pinned OpenSSL copies run `openssl s_client` with host network, for one handshake to the app's own lab server on 127.0.0.1 only.
- A dependency list (CycloneDX or SPDX) is data. Nothing in it runs, and nothing connects to the customer's systems.
- Adam's Otto harness (phase 5c) is one pinned commit, named in `backend/otto.lock.json`. Only the prepare step fetches it; the app never does. It is checked against the pinned fingerprint before it is used, and a copy that differs is not used. It is not software under test, and it starts only our own scripts (the research agent command, the trial script and the two record checkers). A trial goes through the app's own lock, run and review path, so a real library still runs only in its container. Moving the pin needs Kevin's OK.
- A test pack, the advisory snapshot and a recorded answer are data. Nothing in them runs. A pack is refused unless its signature holds, its signer is a trusted key (`backend/app/otto/trusted-pack-keys.json`, or this computer's own key for a pack built here), every design in it can be run by this version, and it follows the installed pack.
- Live Otto: the API key is read only from the `ANTHROPIC_API_KEY` environment variable, at the moment of a call. Never store, show or log it, and never put it in evidence, a ledger or a screenshot. A live call is made only by a person's click (**Connect demo code**) or by the research command with `--live`. It sends the advisory text and, for a fix to the customer's own code, the source file of the failing program and the cases it got wrong; nothing else. No test may reach Claude's API (`backend/tests/conftest.py` blocks it; a test of the live path uses a stand-in).
- Never print secrets or keys in code, logs, docs or replies. Test keys only.
- Ask before adding any dependency not in docs/SPEC.md section 3. (Otto's live call uses Python's standard library; Anthropic's official package would be a new dependency.)

## Commands

- Isolated mode: when Docker is running, `./run-demo.sh` prepares the test images once (including the pinned nginx lab image and one image for each real library; the first time this downloads a few hundred MB and can take several minutes) (`cd backend && .venv/bin/python -m app.prepare`; add `--check` to only report). Only that step may pull or build; the app never does. Without Docker or the images the app runs in demo mode and says why. Force a mode with `EVIDENCE_LAB_MODE=demo` or `isolated`.
- Otto (phase 5c): `./run-demo.sh` also fetches Adam's Otto harness at its pinned commit and checks its fingerprint (`cd backend && .venv/bin/python -m app.prepare --otto`; add `--check` to only report; it needs read access to `isogeny-labs/otto` once, and no Docker). Only that step may fetch it. Without it the app works and says "Otto is not installed on this computer" with the reason, and advisory checks can't be added or run. In a Codespace, `.devcontainer/devcontainer.json` asks GitHub for that read access when a new Codespace is created; the key for Live Otto is a Codespaces secret named `ANTHROPIC_API_KEY`.
- The Otto pin: `cd backend && .venv/bin/python tools/otto_pin.py show`, `check` (Otto's own tests and its audit, run from the pinned copy) or `bump COMMIT [--source DIR]` (needs Kevin's OK, like any dependency change; then run `check`, the backend tests and the accuracy check).

## Tests
- One folder per feature (`backend/tests/dependencies/`, `backend/tests/otto/`), not one file per phase.
- Test wording rules (every answer has a label and a reason; no "secure", no score), not exact sentences, except where a sentence is the requirement.
- The fast set stays under 5 minutes.
- Each feature gets screen tests and one end-to-end walk.
- Every table with a side panel is measured at 1440 pixels wide, panel open and closed: no sideways scrolling and no name broken between letters.
- Every new file reader gets a seeded fuzz test (damaged copies: a plain refusal or a normal read, within a time limit; no new package).
- A test that needs the Otto harness is marked `@pytest.mark.needs_otto`. Where the harness is not installed it is skipped, and the run prints one line with the count ("Otto is not installed here (...): N tests skipped."). Never a silent pass.
- No test reaches Claude's API or needs a key: tests replay the recorded answers, or answers written for the test.
